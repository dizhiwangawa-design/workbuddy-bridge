## 一、任务

修复 `/v1/responses`（以及后续 Chat / Anthropic）在**长任务中途被截停**的 bug：

模型在连续执行多步任务时，会因一条「宣布下一步」的纯文字回复而结束回合，
客户端据此把控制权交还用户，用户必须手动打「继续」才能往下走。

**这是判定层级的问题，不是提示词层级的问题。** 提示词侧的补救已经全部试过且无效，
不要再改 `src/continuation-nudge.js` 的文本或注入位置。

## 三、根因（已用实测证据定死）

### 3.1 因果链

```
模型执行了十几步工具调用
  → 中途产出一句「接着把 manifest 挂到 Sync 路由」   ← 语义上完全符合续跑约束规则 2
  → 但这条回复没有工具调用
  → finish_reason = stop
  → 客户端规则：本轮无工具调用 = 任务结束
  → 回合终止
```

### 3.2 为什么改提示词没用（三次尝试全部失败，别再重复）

| 尝试 | 结果 |
| --- | --- |
| 把约束挪到消息列表末尾 | 无效，且引入了新问题，已回退 |
| 把约束挪回「最后一条 user 之后」 | **同样无效** |
| 重写规则 2（禁止只说不做） | 无效 |

**关键证伪实验**：把一条可验证指令（"回复必须以 BANANA 开头"）分别放在
首个 system / 中途 system / 列表末尾 system / 拼进末尾 user —— **四种位置 4/4 全部被遵守**。

结论：约束确实送到了，模型也确实读了。**问题不在送达，而在它管不住客户端的判定规则**。
模型对「里程碑完成」和「任务完成」的区分不稳定，上下文吃满时更倾向总结收尾。

### 3.3 实测数据

**codex**（`~/.codex/sessions/2026/11/22/rollout-…-01a2023e…jsonl`，270 次请求）

| 截停时刻 | 上下文占比 |
| --- | --- |
| 08:23:38 | 77.5% |
| 08:28:11 | 86.5% |
| 08:43:45 | 89.4% |
| 08:48:10 | 92.6% |
| 16:10:04 | 92.2% |

窗口 486400，会话结束时占 92.6%。9 次纯文字收尾中，8 条正文里带着
`<prior_reasoning>We need continue…` 这类自我说服 —— 模型在反复对自己重申约束并消耗输出预算。

**dsh**（本机 dsh 会话）

- 9 次纯文字步里 **7 次是任务真正完成后的正常总结**
- 只有 2 次是真截停：`turn 10 step 19`、`turn 11 step 24`
- 两次形态一致：连续十几步工具调用 → 突然一步只有文字 → `turn/end: completed`

**顺带排除的干扰项**：dsh 会话里的 `turn/end(completed)` 有 8 次是真的做完了；
唯一一次 `error` 是号池 `429 rate_limit` + `POOL_EMPTY`（账号问题，与本 bug 无关）。
**不要**把 429 也归到这个 bug 里。

## 四、修复方案：桥接层强制续跑

### 4.1 判定（保守，宁可不续）

只在**全部满足**时触发续跑：

| 条件 | 理由 |
| --- | --- |
| `finish_reason === 'stop'` | `tool_calls` / `length` 走原有逻辑 |
| 本次请求声明了 tools | 无工具的纯问答不该续 |
| `tool_choice !== 'none'` | 客户端明确禁用工具时不能硬顶 |
| 本轮 `calls.length === 0` | 有工具调用就是正常回合 |
| 正文命中**宣布型**模式 | 见下 |
| 本轮尚未续跑过 | 最多 1 次 |

**宣布型模式**（中英混合，需覆盖实测措辞）：

```
接下来 / 下一步 / 接着 / 现在(我)?(去|来|就)?(把|补|改|加|写|跑|看) / 我会 / 我将 / 我先 / 继续
let me / i'll / i will / next / now (i|we) / then i
```

- 判定应落在**正文末尾若干字符**，不是整段任意位置（避免正文中间提到「接下来」就误触发）
- 现有 4 个通过用例定义了「安全侧」：`任务全部完成，测试通过。` / `All steps are complete; tests pass.`
  / `修好了，共改动 3 个文件，没有遗留问题。` / `完成。` —— 这些**必须继续不触发**

### 4.2 续跑

追加一条 user 消息后**再请求一次上游**（同一账号、同一租约，**不要重新 pick 账号**）：

```
继续。直接执行下一步，不要再描述计划或复述已经做过的事。
```

要点：
- 计入现有 `totalTimeoutMs`，不是独立的超时预算
- 必须响应 `cancelKind`（用户中断时立刻放弃续跑）
- 最多重试 1 次；第二次即使仍是纯文字也必须收尾（有现成用例守着）

### 4.3 合并

新一轮的产出要接在**同一个 `response`**里：

- 工具调用合并进 `output`，`call_id` 保持唯一（复用现有 `normalizeToolIds` 思路）
- 正文若以重复的说明开头，剥掉重复段再拼接（有专门用例守着）
- `output_index` 必须与终态 `output` 下标一致（`alignLiveOutputIds` 已保证，别破坏）
- 流式与非流式**都要支持**（不带 `stream:true` 时桥接返回普通 JSON，不是 SSE）

### 4.4 开关与可观测性

- 配置项 `continuationRetry`，默认 `true`
  - 加入 `src/api-settings.js` 的 `BOOLEAN_FIELDS`
  - 加入 `src/paths.js` 的 `defaultConfig().apiCompat`
  - 支持 `WB_CONTINUATION_RETRY=0` 应急关闭（照抄 `continuation-nudge.js` 的优先级写法）
- 统计：记录「截停次数 / 已续跑 / 续跑后完成」，进 stats，便于验证效果
  - **没有这个数字就无法判断修复是否有效**，不要省

## 七、禁止事项

1. **不要再改 `src/continuation-nudge.js` 的文本或注入位置** —— 已证伪，改了只会重蹈覆辙
2. **不要为了「让测试变绿」而放宽判定** —— 4 个通过用例是防误伤的护栏，放宽会导致用户永远收不到最终答复
3. **不要把续跑做成无限循环** —— 上限 1 次，第二次纯文字必须收尾
4. **不要在续跑时重新 pick 账号** —— 同一租约内重试，否则号池会计错账
5. **不要顺手改 `encrypted_content` / `previous_response_id`** —— 不在本次范围
6. **不要 fake 掉 `finish_reason`** —— 客户端会因此误判工具调用状态
